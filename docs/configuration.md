# Configuration reference

## Location and format of `.github/docs-pages.config`

Place the settings file at `.github/docs-pages.config`, relative to the root of your repository
(running `npx github:akilasatolu/tsuzuri#v1 init` generates it; see the
[CLI reference](./cli.md)).

The format is simple text in the form `KEY=VALUE`, one item per line. Lines starting with `#`
and empty lines are skipped (use them freely for comments and spacing). YAML-style nesting,
quoting and multi-line values are not supported. Spaces around the value are removed, and
values containing `'` or `"` are used as they are (the quotes become part of the value). Keys
not in the list below are ignored with a warning. Only lines that start with `#` are comments.
A `#` written after the value, as in `THEME=nineties  # 90s style`, is not a comment; it's read
as part of the value, so be careful (write comments on their own line).

## Settings

### TRIGGER_BRANCH
The name of the branch that triggers deployment. The default is `main`. Deployment to GitHub
Pages runs only when there's a push (including merges) to this branch (for manual runs
(`workflow_dispatch`) this check is skipped and it always deploys; see
[Deployment](./deployment.md)). If you set a branch other than the default branch (usually
`main`), extra settings are needed on GitHub (see "Using a branch other than the default branch
as the trigger branch" in [Deployment](./deployment.md)).

### ROOT_MD
The path, relative to the repository root, of the Markdown file that is the starting point of
the site. The default is `README.md`. If the file doesn't exist or points outside the
repository, the build exits with an error.

### OUT_DIR
The folder where the built HTML is written. The default is `_site`. Set a subfolder inside the
repository. If you set a path outside the repository or the repository root (`.`), the build
exits with an error so existing files aren't overwritten. If the key is left out or the value
is empty, it's `_site` too (with workflows from v1.3.0 or earlier, leaving it out makes the
upload to GitHub Pages fail, so write `OUT_DIR=_site`).

The build puts a marker file (`.tsuzuri-build`) in the output folder. On the next build, if the
marker is there, everything in the output folder is deleted before writing, so deleted or
renamed pages don't linger (v1.5.0 or later). Folders without the marker (a folder containing
files you made yourself, for example) are not deleted.

### STYLE_FILE
The path to your custom CSS file. The `.github/docs-pages.config` generated by
`npx github:akilasatolu/tsuzuri#v1 init` sets `.github/tsuzuri/styles/custom.css` (the same
folder as the built-in theme CSS). If you leave the key out, it's the same
`.github/tsuzuri/styles/custom.css`. If the file doesn't exist it simply isn't used (no
warning), so you don't need to create it if you don't need custom CSS. Of the three-layer
cascade (base CSS → THEME → STYLE_FILE), this is the layer with the highest priority, "loaded
last and applied on top". If the file doesn't exist, nothing happens and the site is built with
the default styles. A path outside the repository (a path starting with `../`, an absolute
path, or a symbolic link pointing outside the repository) is ignored with a warning. See
[Theming](./theming.md) for details.

### THEME
Chooses a built-in theme (a set of colors and decoration). The eight possible values are
`material` (the default), `glass`, `neumorphism`, `editorial`, `minimal`, `blueprint`,
`nineties` (90s) and `none` (no decoration). If left out (no key, or an empty value), it's
`material` without a warning. Any other value (a name that doesn't exist, such as `sepia`)
falls back to `material` with a warning. See [Theming](./theming.md) for what each theme looks
like.

### LANGUAGES
The languages of the site (v1.28.0 or later). Write language tags (BCP 47) such as `ja`, `en`
and `pt-BR`, separated by commas.

```
LANGUAGES=en
```

- **The first language is the "base language"**. It's used as the language of the starting
  Markdown (`ROOT_MD`) and of files without a language mark. Put the language of your README
  first.
- With one language you get a single-language site, and the `<html lang="...">` of the output
  HTML and the fixed interface text (such as "Menu") are in that language.
- With two or more languages (e.g. `LANGUAGES=en,ja`) you get a multilingual site. See
  [Multilingual sites](./i18n.md) for how to arrange the files.
- If left out (no key, or an empty value), it's `en` (English) without a warning. **This changed
  from the default `ja` used up to v1.27.0.** If your README is in Japanese, write
  `LANGUAGES=ja`.
- Spaces around each language are removed. Values that aren't valid language tags, such as
  `en_US`, and values that duplicate another regardless of case, are ignored one by one with a
  warning. If no valid value remains, it's `en` with a warning.

The language of a page is decided by its file name and `LANGUAGES`, and can't be changed in the
frontmatter (see [Multilingual sites](./i18n.md) for details).

> [!NOTE]
> The setting key `LANG` used up to v1.27.0 has been removed. If it's in the settings file, it's
> ignored with a warning (it isn't read as `LANGUAGES`). If you wrote `LANG=ja`, rewrite it as
> `LANGUAGES=ja`. The OS environment variable `LANG` (such as `ja_JP.UTF-8`) isn't used either.

### NAV_ENABLED
Whether to output the automatically generated page navigation (a list of links to every page on
the site). Only `true` or `false` (case-insensitive) are valid, and the default is `false`. If
left out (no key, or an empty value), it's `false` without a warning. Any other value (e.g.
`yes`) is treated as `false` with a warning.

The navigation is a hierarchy (nested lists) that follows the folder structure of the
repository. Folders can be collapsed by clicking them (v1.7.0 or later). At first every folder
is open, so links to every page are visible whichever page you're on (v1.14.0 or later; from
v1.7.0 to v1.13.0, only the top level and the folder containing the current page were open).
On wide screens (960px or more) it's a sidebar fixed on the left; on narrow screens
(smartphones and so on) it's a "Menu" button above the content, and pressing it opens the page
list (no JavaScript is used). The button reads "メニュー" if the page language is Japanese and
"Menu" otherwise.

Each page also gets links to the "previous page" and "next page" at the end of the content, in
navigation order, and a site search box appears at the top of the navigation (see
[Concepts](./concepts.md#site-search)). Pages with three or more headings also show an in-page
table of contents (see [Concepts](./concepts.md#links-to-headings-and-the-table-of-contents)).
Next to the navigation header there's a button that switches between light and dark (see
[Concepts](./concepts.md#switching-between-light-and-dark)).

Settings files newly created with `npx github:akilasatolu/tsuzuri#v1 init` have it set to
`true` (v1.7.0 or later).

```
README.md             … page (link)
docs                  … folder (heading)
  getting-started.md
  guides              … subfolder (heading)
    install.md
```

- **Page names**: the frontmatter `title` is used. For pages without a `title`, the first
  `# heading` (h1) in the text is shown, or the file name (e.g. `getting-started.md`) if there's
  none. For pages where you want a different name only in the navigation, write a `title` (see
  the [frontmatter reference](./frontmatter.md#title)).
- **Order**: the order in which pages were found by following links from the starting Markdown.
  They're listed in the order you wrote the links in the README and other pages. A folder is
  placed at the position of the first page found in it.
- **Pages listed**: only pages reachable by links from the starting point are listed (Markdown
  that isn't linked is in neither the navigation nor the site, even in the same folder).

### FAVICON_FILE
The path, relative to the repository root, of the favicon image used by the generated site. If
not set, no `<link rel="icon">` tag is output (the site has no favicon). If the file doesn't
exist, the build continues without a favicon, with a warning. A path outside the repository (a
path starting with `../`, an absolute path, or a symbolic link pointing outside the repository)
is ignored with a warning. Note that this is the favicon you set for your site; it has nothing
to do with Tsuzuri's own logo and favicon (under `assets/`).

### SITE_NAME
The site name used in `<meta property="og:site_name">` on every page and as the site title at
the top of the navigation when the navigation is enabled. If the starting page (`ROOT_MD`) has
neither a frontmatter `title` nor a first `# heading` (h1), it's also used as that page's title
and its name in the navigation (frontmatter in `README.md` is shown as a table on GitHub, so
this lets you avoid writing it). If left out, the repository name, the part after `/` in the
environment variable `GITHUB_REPOSITORY` at build time (in the form `"owner/repo"`; a default
environment variable always set on GitHub Actions), is used automatically. If
`GITHUB_REPOSITORY` itself doesn't exist (when running locally, for example), it stays empty.

### CUSTOM_DOMAIN
The domain name when using a custom domain (without a scheme, e.g. `docs.example.com`). When
set, a `CNAME` file is generated automatically right under the output folder. A value that
isn't a valid host name (a value with `https://` or containing a path, for example) falls back
to empty with a warning, and no `CNAME` is generated. See [Deployment](./deployment.md) for
details.

### OGP_DEFAULT_IMAGE
The default OGP image used for pages that don't set `ogImage` in the frontmatter (a path
relative to the repository root, or an absolute URL). If left out, pages without `ogImage` get
no `og:image` tag at all.

A relative path is converted to an absolute URL of the site, like
`https://<owner>.github.io/<repo>/assets/ogp.png`, and the image file is copied to the site too
(social media only load OGP images from absolute URLs). A path pointing outside the repository
is ignored with a warning.

### STRICT_LINKS
Whether to fail the build when there are link problems. `true` or `false` (case-insensitive),
and the default is `false`.

- `false` (the default): link problems such as broken links only produce warnings, and the site
  is published anyway.
- `true`: if any of the following is found, the build exits with an error. The workflow stops
  there and the site isn't updated (the previously published content stays).
  - A linked Markdown file doesn't exist (a broken link)
  - A link that wasn't followed, for example because it points outside the repository
  - A linked image or file doesn't exist or can't be copied
  - The output path of a linked file collides with a generated page or a file Tsuzuri creates
    (such as `index.html`) (v1.4.0 or later)
  - The heading in a link to a heading (`page.md#heading`) doesn't exist on the target page
    (v1.5.0 or later)

The list of problems is shown in the workflow run log in the Actions tab.

### LAST_UPDATED
Whether to show the last updated date (the date the Markdown file was last committed in git) at
the end of each page. `true` or `false`, and the default is `false` (not shown).

With `true`, the workflow fetches the full git history before building (this takes a little
longer for repositories with a long history). If the git history can't be read, the build
continues without dates, with a warning.

### EDIT_LINK
Whether to add an "Edit this page on GitHub" link at the end of each page (v1.30.0 or later).
`true` or `false`, and the default is `false` (no link).

With `true`, the link opens the page's Markdown file in GitHub's editor, so readers can fix a typo
or an outdated sentence on the spot and send the change (people without write access to the
repository are guided through making a fork and a pull request by GitHub). On English pages the
link reads "Edit this page on GitHub"; on Japanese pages, "このページを GitHub で編集". If
`LAST_UPDATED=true`, it's shown on the same line as the last updated date. The 404 page doesn't
get it.

The link points to the branch that was built: on GitHub Actions, the branch that was pushed (the
`TRIGGER_BRANCH`); locally, the current branch and git's `origin`. If the branch isn't known
(building a tag, or no `origin`, for example), a warning is shown and no links are added. This
site uses `EDIT_LINK=true`.

### SITEMAP_JSON
Whether to output the debugging `sitemap.json` (the collected pages and images, the list of
broken links and so on). `true` or `false`, and the default is `false` (not output). With
`true` it's included in the public site too, and things like the names of broken link targets
are visible to anyone, so we recommend setting it to `true` only temporarily while
investigating (see "About sitemap.json" in [Concepts](./concepts.md) for details).

## Backward compatibility

The eleven keys `LANGUAGES`, `NAV_ENABLED`, `FAVICON_FILE`, `SITE_NAME`, `CUSTOM_DOMAIN`,
`OGP_DEFAULT_IMAGE`, `THEME`, `STRICT_LINKS`, `SITEMAP_JSON`, `LAST_UPDATED` and `EDIT_LINK` are
**all optional**. If you set none of them, all the defaults above apply, and the behavior is the same
as the versions before these keys were introduced. You can keep using an existing settings file
(with only the original four keys) without anything breaking.

The site language is the one exception. v1.28.0 removed `LANG`, and the default when no
language is written changed from `ja` to `en`. With a settings file that doesn't write
`LANGUAGES` (including one that only writes `LANG=ja`), the site becomes an English site
(`<html lang="en">` and English interface text). For a Japanese site, add `LANGUAGES=ja`.
